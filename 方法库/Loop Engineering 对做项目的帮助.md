## 我能借鉴什么

Loop Engineering 跟 CLAUDE.md 现有原则不冲突，是升级和补充。以下是四个层面的具体升级路径。

---

## 层面一：任务描述升级（立即可用）

### 改变前

```
帮我修这个 bug
把这个功能优化一下
给财务系统加个报表
```

### 改变后

```
修这个 bug，完成后跑 python -m pytest test_xxx.py，全部通过才算完
优化这个功能，目标：接口响应 < 200ms，错误率 < 0.1%
给财务系统加报表，对照 01-data-model.md 中的表结构，字段名必须一致
```

### 关键转变

把"做好"替换为**可被机器验证的条件**。这就是最小单位的 Loop。

---

## 层面二：项目流程升级（复杂项目用）

### 已有的

"先出设计文档再写代码"（6 份明细文档 → 人工确认 → 按文档写代码 → 校验）

### 升级后

设计文档里的 **API 契约、数据 schema、状态枚举** 不仅是给人看的，也是给 Agent 当验证标准的：

```
现在按 06-api-contract.md 写后端代码。
约束：
- 每个端点写完后，对照文档验证请求/响应 schema 是否一致
- 字段名、类型、必填/可选必须跟文档完全一致
- 不允许新增文档里没定义的端点
完成后跑 npm run test，全部通过才算完成。
```

### 关键转变

设计文档从"仅供参考"变成"可验证的契约"。

---

## 层面三：质量保障升级

### 已有的

CLAUDE.md 原则 4「目标驱动执行」——定义成功标准，循环验证直到达成。

### 升级后

加入「做 + 验」双 Agent 模式：

- **一个 Agent 写代码**（按设计文档，只做文档里定义的事）
- **另一个 Agent 验证**（用不同角度检查：文档一致性、边界情况、安全自检）

验证 Agent 的 prompt 示例：
```
你是代码审查者。逐条检查：
1. 所有接口签名是否与 06-api-contract.md 一致
2. 所有字段名是否与 01-data-model.md 一致
3. 是否引入了文档未定义的功能
4. 安全自检清单 17 项是否全部通过
列出所有不一致的地方。
```

### 关键转变

写代码和验证代码由不同 Agent 负责，防止"自己批自己考卷"。

---

## 层面四：自动化升级（成熟后启用）

### 定时任务

- 当前：你说"财务数据来了"，Agent 才动
- 升级后：定时任务每天早上自动检查数据目录，有新文件就自动跑分析

- 当前：每次手动跑 /neat 整理
- 升级后：Hook 配置，每次 Agent 会话结束后自动跑整理

### 工作树隔离

- 当前：单 Agent 串行改代码
- 升级后：多个 Agent 在独立工作空间并行工作，互不干扰，干完合并

---

## 四个层面汇总

| 层面 | 核心变化 | 立即可用？ |
|---|---|---|
| 任务描述升级 | 把"做好"替换为机器可验证的条件 | ✅ 现在就用 |
| 项目流程升级 | 设计文档从参考变成可验证契约 | ✅ 下一个复杂项目就用 |
| 质量保障升级 | 做 + 验双 Agent 分工 | ⚠️ 关键项目启用 |
| 自动化升级 | 定时任务 + 工作树 + Hook | ⏳ 熟练后再上 |

---

## 跟现有 CLAUDE.md 四原则的关系

| 现有原则 | Loop Engineering 补充了什么 |
|---|---|
| 编码前思考 | 思考的结果要写成**可验证的完成标准**，不只是"想清楚" |
| 简洁优先 | 边界条件划定后，"没在目标里的不做"变得更具体 |
| 精准修改 | 有契约约束后，精准度进一步提升 |
| 目标驱动执行 | 验证自动化——从"你手动跑测试"变成"Agent 自己跑" |

---

## 一句话总结

> Loop Engineering 对我做项目的核心帮助：**把 CLADE.md 的"目标驱动执行"原则升级为"机器可验证的目标驱动执行"。** 从"想清楚再写"变成"写清楚验证条件再写"。
