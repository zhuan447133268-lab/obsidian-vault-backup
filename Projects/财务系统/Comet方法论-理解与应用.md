## 一、Comet 方法论核心思想

**Comet** 是一个 AI 驱动的软件开发流程编排器，核心理念是**将"定义做什么"和"实现怎么做"彻底分离**：

```
┌─────────────────────────────────────────────────────┐
│                    Comet 编排层                       │
│                                                       │
│   OpenSpec (WHAT)          Superpowers (HOW)          │
│   ┌─────────────────┐     ┌─────────────────┐        │
│   │ 提案管理          │     │ 头脑风暴          │        │
│   │ 规格生命周期      │     │ 设计文档          │        │
│   │ 差异规格          │     │ 实施计划          │        │
│   │ 归档              │     │ TDD              │        │
│   └─────────────────┘     │ 代码审查          │        │
│                            └─────────────────┘        │
│                                                       │
│   五阶段自动化流水线:                                   │
│   Open → Design → Build → Verify → Archive            │
└─────────────────────────────────────────────────────┘
```

### 关键理念

1. **先定义 WHAT，再实现 HOW**：需求不清晰不动手，设计不完整不写代码
2. **文档先行**：在写任何代码之前，先产出完整的设计文档
3. **机器可验证**：每个阶段的产出必须可验证（不是"感觉对了"，而是"检查通过"）
4. **增量归档**：每个变更都有明确的规格差异记录，可追溯

## 三、本项目的6份明细文档定义

结合经营分析看板模块的实际需求，将 Comet 方法论映射为以下6份文档：

### 文档1：数据模型设计

**核心问题**：需要几张新表？每张表存什么？与现有表的关系？

具体内容：
- `analysis_uploads` — 上传批次表（记录每次6张表的上传）
- `analysis_raw_data` — 原始数据存储表（6张表解析后的原始行数据）
- `analysis_garden_data` — 园所数据表（按园所拆分后的汇总数据）
- `analysis_dashboard_cache` — 看板数据缓存表（预计算的图表数据JSON）
- 与现有 `companies` 表的关联（通过园所编码 code）
- 与现有 `users` 表的关联（上传人、查看权限）
- 索引设计、分区策略

### 文档2：后端架构设计

**核心问题**：新增哪些文件？包结构如何？关键接口签名？

具体内容：
- 新增包：`internal/handler/analysis_*.go`、`internal/service/analysis_*.go`、`internal/repository/analysis_*.go`
- 新增 model：`analysis_upload.go`、`analysis_garden_data.go` 等
- 不改动任何现有文件（新增路由在 main.go 中追加，不动已有路由）
- 状态机设计：上传→解析→拆分→计算→生成→完成
- 并发控制：90+园所并行计算
- Excel 解析库选型：`excelize`（已有依赖）

### 文档3：数据处理管线设计

**核心问题**：6张Excel如何一步步变成看板数据？

具体内容：
- 入口：出纳管理员上传6张表 → 临时存储
- 阶段1：Excel解析 → 读取每个Sheet → 提取表头映射 → 标准化为统一行格式
- 阶段2：数据校验 → 必填列检查 → 园所编码匹配 → 数据范围校验
- 阶段3：园所拆分 → 按园所编码分组 → 每个园所提取关键指标
- 阶段4：指标计算 → YTD累计/当月/预算/同比 → EBITDA/利润率/人工占比等
- 阶段5：看板数据生成 → 图表数据JSON → 写入缓存表
- 失败重试机制、错误记录

### 文档4：看板生成运行时设计

**核心问题**：看板数据如何计算？图表如何配置？缓存如何更新？

具体内容：
- 单个园所看板的数据计算逻辑（8个图表的数据来源和计算公式）
- 集团整体看板的数据聚合逻辑
- Excel报告的生成逻辑（6个Sheet的数据填充）
- 图表配置结构（ECharts option JSON）
- 缓存策略：上传后一次性计算全部，查询时直接读缓存
- 数据版本管理：同一月份多次上传覆盖

### 文档5：前端设计

**核心问题**：新增哪些页面？组件如何组织？路由和权限如何配置？

具体内容：
- 新增页面清单：
  - `AnalysisUpload.vue` — 出纳管理员：上传6张表+触发处理
  - `AnalysisDashboard.vue` — 看板查看入口（按角色显示不同内容）
  - `GardenDashboard.vue` — 单个园所看板展示
  - `GroupDashboard.vue` — 集团整体看板展示
  - `GardenConfig.vue` — 园长-园所映射配置
- 路由配置（新增角色权限）
- 侧边栏新增"经营分析"模块
- 组件复用：状态看板卡片、筛选器、图表容器
- 上传进度跟踪UI
- Excel在线预览（可选）

### 文档6：接口契约设计

**核心问题**：新增哪些API？请求/响应长什么样？

具体内容：
- 上传相关：`POST /api/v1/analysis/upload`、`GET /api/v1/analysis/uploads`
- 看板相关：`GET /api/v1/analysis/garden/:code`、`GET /api/v1/analysis/group`
- Excel下载：`GET /api/v1/analysis/garden/:code/excel`、`GET /api/v1/analysis/group/excel`
- 配置相关：`GET/PUT /api/v1/analysis/principal-mappings`
- 每个端点的完整 Request/Response JSON Schema
- 错误码定义

## 四、五阶段流水线在本项目的落地

```
Open (需求定义)          Design (设计)           Build (开发)
┌──────────────┐       ┌──────────────┐       ┌──────────────┐
│ 业务需求梳理   │  ──→  │ 6份明细文档   │  ──→  │ 按文档写代码  │
│ (已完成)      │       │ (本次产出)    │       │ (后续)       │
└──────────────┘       └──────────────┘       └──────────────┘
                               │                       │
                               ▼                       ▼
                        Verify (验证)           Archive (归档)
                       ┌──────────────┐       ┌──────────────┐
                       │ 对照文档逐条   │  ──→  │ 代码合并归档  │
                       │ 验证实现      │       │ 规格差异记录  │
                       └──────────────┘       └──────────────┘
```

### 各阶段可验证的完成标准

| 阶段 | 验证方式 |
|---|---|
| Open | 业务需求文档已获阳阳确认 ✓（已完成） |
| Design | 6份文档完整、无歧义、可直接指导开发 |
| Build | 代码通过编译、不破坏现有功能 |
| Verify | API 接口测试通过、前端页面可访问、权限正确 |
| Archive | 代码合并、Obsidian 归档、更新 [[余额表系统-现有业务流程梳理]] |

## 五、与现有 CLAUDE.md 原则的对齐

Comet 方法论与项目已有的开发原则高度一致：

| Comet 理念 | 对应 CLAUDE.md 原则 |
|---|---|
| OpenSpec 定义 WHAT | 原则1「编码前思考」— 明确假设、呈现权衡 |
| 文档先行 | 原则5「先出设计文档再写代码」 |
| Superpowers 实现 HOW | 原则2「简洁优先」— 最少代码解决问题 |
| 不改动现有代码 | 原则3「精准修改」— 只碰必须碰的 |
| 可验证的完成标准 | 原则4「目标驱动执行」— 机器可验证 |
