## 1. 考试详情页未参加学生状态显示「草稿」

- **坑**：教师端考试详情页，未参加考试的学生状态映射为「草稿」，与考试自身状态 DRAFT 语义混淆。
- **根因**：`PaperStatus.DRAFT` 原本表示「试卷已生成、学生尚未开考」（学生端显示「待考」、统计端显示「未开始」），但教师端详情页把它映射成了「草稿」。
- **修复**：教师端该列状态改为「待考」（`268e5ad`）。
- **验证**：测试环境教师端考试详情页已确认显示「待考」。

## 2. 登录页信息冗余（「欢迎登录」标题）

- **坑**：登录页同时存在系统名与「欢迎登录」两级大标题，视觉层级冗余。
- **根因**：页面结构多套了一级标题 + 提示行。
- **修复**：移除「欢迎登录」标题及提示行，保留 logo + 系统名 + 标语 + 表单的单层结构（`dd3254d`）。
- **验证**：测试环境登录页已确认无「欢迎登录」，层级干净。

## 3. 账号被禁用后旧 token 仍可继续操作

- **坑**：管理员禁用教师账号后，教师未刷新页面，用旧 token 仍能发布/关闭考试。
- **根因**：`JwtStrategy.validate` 只校验了签名与 token 黑名单，没有查询用户状态；禁用只影响下次登录。
- **修复**：每次受保护请求都校验用户 `status`，`status=0`（禁用）返回 `401 + code 1005「账号已被禁用」`；前端拦截器对 1005 提示并清除登录态跳转登录页，不再尝试刷新 token（`8caf336`）。
- **验证**：测试环境完整走通——禁用教师 → 教师旧会话点「发布」→ 收到 1005 被拦，考试保持草稿未发布。
- **避坑提醒**：凡「禁用/停用」类操作，只改数据库状态是不够的，必须同步拦截已发放的 token（状态校验放在鉴权策略里，而不是只在登录时判断）。

## 4. 禁用账号被踢回登录页，无任何提示

- **坑**：账号被禁用后直接跳转登录页，`ElMessage.error` toast 一闪而过/根本没显示，老师不知道发生了什么。
- **根因**：`ElMessage.error(...)` 之后立即 `window.location.href = '/login'`，整页卸载把 toast 杀掉，提示永远来不及渲染。
- **修复**：改为 `ElMessageBox.alert` 模态弹窗明确告知「账号已被禁用」，用户确认后再清除登录态并跳转；加 `isKicked` 防重，避免禁用后并发请求（多个 1005）重复弹窗（`b321bb7`，文件 `web/src/api/request.ts`）。
- **验证**：测试环境复验——禁用教师后点发布，弹出「账号已被禁用」模态框，点「去登录」才跳转 /login，sessionStorage 清空。
- **避坑提醒**：**先弹提示、确认后跳转**，任何「提示 + 立即跳转」的组合都会丢提示。用 `ElMessageBox.alert.then(跳转).catch(跳转)` 保证确定/关闭都跳转。

## 5. 新增/导入教师工号可撞已有学生学号（反之亦然）

- **坑**：管理端新增教师，工号填系统中已存在的学生学号（或导入时学号撞已有工号）仍创建成功，人工误录无从拦截。
- **根因**：`createUser` 唯一性预检只在**同名字段**内查重（创建教师查 staffNo、创建学生查 studentNo）。staffNo 与 studentNo 是互相独立的数据库唯一索引、互不感知，跨字段撞号数据库不报错。
- **修复**：
  - `createUser` 预检改为跨 staffNo/studentNo 双字段 OR 查重，任一命中即报 `1501「学号/工号已存在」`；
  - 批量导入教师/学生两处同步跨字段查重，撞到异类字段按行报错跳过，不创建、不更新错误用户；
  - 新增 3 个单测覆盖（教师撞学生学号、学生撞教师工号、OR 双字段断言）（`c41c9f8`）。
- **验证**：单测先红后绿；server 套件 54/54 通过；SQL 验证 OR 语义真实命中（工号=2307710116 → 学生李喆）；测试环境管理端复验——工号填 2307710116 被拒绝「学号/工号已存在」，无脏数据，李喆保留。
- **避坑提醒**：**同一身份编号池的字段（工号/学号）必须跨字段查重**。预检写成 filter 去 undefined 再 OR 是「只查同名字段」的典型错误；唯一性校验要站在业务语义（同一人选）而非数据库字段上看。

## 6. 统计导出与页面列表口径不一致

- **坑**：教师班级统计导出数据与页面显示的列表不一致。
- **根因**：导出未支持 keyword 搜索结果、且每生不是一行，与列表查询口径不同。
- **修复**：导出与列表同口径——支持 keyword 搜索、每生一行（`b6fec42`）。
- **验证**：上午修复，尚未在测试环境复验（待后续）。

## 7. createdAt 相同导致分页重复/漂移

- **坑**：列表 createdAt 相同时排序不稳定，翻页出现重复/丢记录（分页漂移）。
- **根因**：查询只用 `createdAt` 排序，同秒创建的多条记录排序不稳定。
- **修复**：分页与最新记录查询统一按 `createdAt + id` 稳定排序，覆盖考试列表、试卷列表、用户列表、学院管理员列表、教师班级关联列表、班级最新考试、学生考试列表、活跃试卷查询等 8 处，`statistics.service.ts` 6 处同步加固（`43f0693`）。
- **验证**：上午修复，尚未在测试环境复验（待后续）。
- **避坑提醒**：**数据库排序字段必须有唯一后手（主键），不能只按时间戳**；凡分页查询必查 `createdAt` 是否可能相同。

## 8. 「标记已提醒」只记时间戳，学生端收不到任何提醒（功能半成品）

- **坑**：教师端缺考名单点「标记已提醒」提示成功，但学生端没有任何提醒——测试期望「学生端可收到考试提醒」落空。
- **根因**：`markAbsenteeReminded` 只更新 `paper.remindTime`，全项目没有任何学生端代码消费该字段；「发提醒给学生」的链路从设计上就不存在（第七阶段提交只做了教师端标记与展示）。
- **修复**：不引入推送基建，改为「提醒卡片」——标记成功后弹对话框展示完整文案（考试名/时间/学生/分享链接），老师一键复制后粘贴到班级群或私发学生；学生点链接进 `/student/exam-share/:id` 分享页查看考试并可去考试（`7c5a2e0`）。
- **验证**：本地全链路自测 + 测试环境回归——本地：教师标记 → 卡片弹出 → 一键复制 → 学生登录点链接看到考试提醒卡片（含考试信息与去考试按钮）；测试环境：test0813（已关闭、40 名缺考）教师标记 → 提醒卡片弹出（文案含考试名/时间/分享链接）→ 一键复制 toast → 缺考名单行变「提醒时间 + 再次提醒」→ 分享链接可打开。
- **避坑提醒**：**任何带「提醒/通知/分享」语义的按钮，验收标准必须包含接收端闭环**；只写一个标记字段不算功能。外部推送渠道（短信/钉钉）缺失时，「老师复制转发」是低成本补齐方案。

## 9. 补考通过的考生仍留在补考安排列表，可被反复生成补考试卷

- **坑**：补考通过后学生仍一直出现在补考安排列表，可反复点击生成补考试卷。
- **根因**：`exam.service.ts` 的 `findMakeupCandidates` 只排除了 `isMakeup=true 且 status in [DRAFT, IN_PROGRESS]` 的补考卷，没排除终态且分数达标的补考卷；补考不消耗次数（`studentAttempt.upsert` 的 usedCount 不递增），次数用尽的学生永远命中 ATTEMPTS_EXHAUSTED 候选。生成侧 `generateMakeupPaperForStudent` 事务内同样只查「未完成补考卷」。
- **修复**：列表侧新增并行查询 `finishedMakeupPapers`，按 `score >= passScore（config.passScore ?? 80）` 生成 `passedMakeupPaperStudentIds` 从候选剔除；生成侧在 `$transaction` 内先 `findFirst` 终态且达标的补考卷，命中直接返回 `{ generated: false }`，不再 `paper.create`（防候选校验后、生成前状态刚变的竞态）（`c46730a`）。
- **验证**：`exam.service.spec.ts` 新增 7 个单测（候选剔除 5 例 + 生成兜底 2 例，含「已有通过卷 → create 未调用」）；未在测试环境复验。
- **避坑提醒**：「次数用尽」这类候选判定不能只看次数与未完成卷，要考虑业务已经达成的终局（已通过）；列表与生成两条链路都要有同一终局兜底。

## 10. 基础数据导入「状态」列未生效，填禁用账号仍为启用

- **坑**：教师/学生 Excel 导入，状态列选「禁用」后账号仍为启用。
- **根因**：`users-import.service.ts` 的 `upsert.create/update` 里 `status` 取的是 `parseStatus(row.student_status)`（学籍状态列，值为「在读/休学」），不是状态列的 `row.status`；且学生模板当时根本没有独立「状态」列。
- **修复**：教师/学生两处 `status` 改为 `parseStatus(row.status)`；学生模板新增独立「状态」列并加下拉校验；ImportSummary 拆出 `createdCount/updatedCount/skippedCount`（`b4e1247`）。
- **验证**：新建 `users-import.service.spec.ts`（275 行，真实 Excel 构造基建），覆盖教师/学生状态禁用写 0、留空默认 1、已有用户按 Excel 状态更新等用例；未在测试环境复验。
- **避坑提醒**：Excel 中文列名与代码 row key 必须逐列对照，警惕「状态」与「学籍状态」这类语义相近的列各取所用。

## 11. 导入结果只剩「成功」总计数，看不出新增/更新/跳过

- **坑**：师生导入结果摘要只显示「成功：N」，用户无法区分新增、更新、跳过。
- **根因**：前端 `data-import.vue` 只渲染 `successCount`，后端此前没有独立的 updated/skipped 计数（#10 才补上字段）。
- **修复**：前端按 `importMode` 分流——UPSERT 显示「新增/更新」，SKIP 显示「成功导入/跳过」；失败>0 时 ElMessage 切 warning（`f2fe0a3`）。
- **验证**：`users-import.service.spec.ts` 新增模式计数 2 例（UPSERT→1 增 1 更；SKIP→1 跳）；前端展示无 e2e，需测试环境人工复验（与 #10 同属基础数据导入流程）。
- **避坑提醒**：计数字段与展示字段要一起演进——后端加了新维度计数，前端渲染与文案必须同步，否则信息到不了用户。

## 12. 证书导出不跟随当前筛选：清空筛选未重新查询时导出了全量

- **坑**：先按筛查询出结果后清空筛选框、不点查询，直接导出 → 导出数据不是表格当前展示的（变成了全量）。
- **根因**：`CertificateExportPanel.vue` 的 `onExportExcel/onExportZip` 直接调 `buildParams()` 实时读表单值，筛选为空时按「空条件=全量」请求，与页面表格（仍是上次查询结果）不一致。
- **修复**：新增 `lastQueryParams` 快照，仅 `onSearch` 查询成功后写入；导出 Excel/ZIP 统一用快照（ZIP 分页循环同样以快照为准），保证导出与表格所见一致（`8f40d77`）。
- **验证**：无自动化测试（16 行 Vue diff），需测试环境复验。
- **避坑提醒**：导出类功能必须绑定「上一次成功查询的参数快照」，不能导出时实时读表单——表单当前值与表格已展示数据本来就不是一回事。

## 13. 不在参考名单的学生扫码可见考试入口、直调 start 能建卷

- **坑**：同班/同院但组卷时未勾选的学生，扫码仍能看到考试入口，直调 start 接口甚至能建卷参加。
- **根因**：`student-exam.service.ts` 的 `getShareInfo`（分享页）只按班级/学院范围校验，漏掉「同班但未勾选」；`start` 无活跃试卷分支直接 `consumeAttempt + createRetakePaper`，从不校验该生在本次考试下是否生成过 Paper。
- **修复**：两处各加 `paper.findFirst({ examId, studentId })` 校验（参考名单以 Paper 记录为准）；无 Paper 抛 `ForbiddenException({ code: 1207 … })`；`start` 先校验再扣次数/建卷（`124e21e`）。
- **验证**：`student-exam.service.spec.ts` 新增 4 例：同班无 Paper 扫码→1207；名单内→正常；无卷直调 start→1207 且 upsert/create 均未调用；有终态旧卷→正常重考入口。测试环境未复验。
- **避坑提醒**：接口级权限校验的「范围」要与业务名单是同一种实体（Paper 记录），用班级/学院这类外围属性当边界必然漏人。

## 14. 基础数据导入切换新 Excel 文件后导入请求根本没发出

- **坑**：el-upload 已有一个文件（limit=1 已满）时再选新文件，统计仍停留在上一次文件的结果，无效。
- **根因**：`data-import.vue` 只绑了 `:on-change`，limit=1 已满后选择新文件走 `on-exceed` 分支，`on-change` 不再触发，导入从未执行。
- **修复**：新增 `:on-exceed="onExceed"`，导入逻辑抽成 `runImport(file)` 两条路径复用（`0b81198`）。
- **验证**：无测试改动，需测试环境复验（与 #19 同属 el-upload limit=1 换文件流程，#19 后续补展示）。
- **避坑提醒**：`el-upload` 的 `on-exceed` 与 `on-change` 是两个互斥分支，limit 已满后所有新选择都走前者，业务处理必须两个分支都覆盖。

## 15. 教师班级统计「状态」筛选与列表列口径不一致，及格线硬编码 80

- **坑**：按「未通过」筛选后列表状态列却显示「已提交」；导出同款不一致；统计模块 9 处硬编码 80 当及格线，考试及格线改为 60 后统计仍按 80 算。
- **根因**：列表行渲染 `paperStatus`（试卷生命周期，「已提交」），筛选下拉用考试结果口径（passed/failed/absent/not_started）；及格线在多处硬编码 `>= 80`，与判分/证书用的 `paperConfig.passScore` 不同源。

## 23. 建考确认连点，一次生成多条一模一样的考试草稿

- **坑**（测试老师原话）：学院管理员账号下点「创建考试」，弹窗填完信息点「确认」，**页面卡顿的时候多点了几次确认，直接生成了好多条一模一样的考试草稿**。
- **根因（三层同时缺保护，缺任一层都会漏）**：
  1. **弹窗组件**：`AppFormDialog.vue` 里早就有一个 `confirmLoading` prop，但**全项目没有任何调用方传它**——确认按钮从来不进 loading/禁用态。这是典型的"留了个半成品属性"。
  2. **调用方**：创建考试的处理函数**没有重入守卫**，且弹窗只在 `await 建考接口` 成功之后才关闭，请求飞行期间弹窗和按钮全程可点。
  3. **后端**：`POST /exams` **零幂等**，`exams` 表也没有业务唯一约束，前端漏几次就落几条。
  - 补充一个容易误判的点：Element Plus 的 `:loading` 是在按钮内部**异步**置 disabled 的（`use-button.mjs` 读 `_disabled || props.loading`），**同一个事件循环 tick 内的第二次点击仍能穿过去**——所以"卡顿连点"不是罕见场景，而是必然重复。
- **修复**：
  - **组件层根治**（未来所有弹窗自动受保护）：`AppFormDialog` 新增 `confirmHandler` prop，点击时**先同步上锁、再 await 回调**，`finally` 释放，失败自动放开以便修正后重试；原来的 `confirm` 事件保留做兼容。
  - **4 个调用方**由 `@confirm=` 改为 `:confirm-handler=`：`teacher/index.vue`（创建考试）、`school-admin/users.vue`（新增师生）、`college-admins.vue`（新增学院管理员）、`school-admins.vue`（新增学校管理员），**处理函数一行没改**。
  - **同类零防重入口一并补齐**（排查中发现的真实风险）：学院管理/专业管理/班级管理的保存、题库导入、基础数据导入——各加"提交中"锁 + 按钮 `:loading` + 入口 early-return。
  - **后端兜底**：`exam.service.ts` 的建考加 **60 秒幂等窗口**，去重键 = `用户 + 考试名 + 学院 + 班级 + 考生类型 + 开始时间`；命中则按 id 重查返回同一条，并发请求用 in-flight promise 共享（沿用项目里既有的进程内 Map 风格，与 `ThrottleGuard` 一致）。
  - **一个 Vue 细节**：不能沿用 `@confirm="fn"` 写新逻辑——它编译成 vnode 的 `onConfirm`，`emit('confirm')` 会把它**再调一次**，所以新属性单独命名为 `confirmHandler`。
- **同批排查到、故意没改的同类风险**（各自根因不同，不是前端防重能解决的）：学生「重新考试」并发会重复建试卷（`Paper` 无唯一约束，需要 DB 唯一键 + 错误码映射）；全局 10s axios timeout 对长耗时导入的放大；`ElMessageBox` 同帧双击叠框；组织（学院/专业/班级）同名**后端没有查重**。

## 27. 考试链路并发：5 处会真实丢数据/错数据的地方（含 Prisma upsert 的坑）

> 触发：业务方追问"要是许多学生同时考试，并发的情况，你考虑过吗？"——审计后确实有问题，下面每一条都配实测证据。

- **① 三处"终结试卷"都是无条件写库**（手动交卷 / 切屏强制交卷 / 每分钟超时扫描）：连点交卷或两种交卷撞车 → 重复判分、重复写事件、重复发证；最阴的是**超时扫描会把刚手动交卷的卷子回头覆写成 TIMEOUT**（分数还在，状态与时间戳被改）。修复：三处统一走 CAS `UPDATE papers SET 终态… WHERE id=? AND status='IN_PROGRESS'`，拿不到就跳过；**并发**交卷的失败方改为**回读已终结状态返回**（不再抛 1404），连点用户看到的结果与首次一致。
  - 补充（2026-09-17 测试环境实测校准两种"重复交卷"是不同的路）：**并发**重复交卷 → 都读到 IN_PROGRESS、放行，CAS 只有一个赢家，其余走"回读终态"返回成功（8 并发实测全部 100 分、1 条 SUBMIT）；**顺序**重复交卷（前一次已落终态）→ 查活跃卷时就没有卷了，接口回 **400 / 1403「试卷不存在或未生成」，零写入**（状态、分数、submitTime、事件数全不变）。原文档写的"不再报 1404"只对前者成立，别把它当成"重复交卷一定回成功"。
- **② `papers.answers` 是整列 JSON，"读整列→改一题→写回整列"**：交卷前前端并发刷写多题答案（`Promise.all`），后写覆盖先写 → **直接丢答案丢分**。修复：保存答案进事务 + `SELECT answers … FOR UPDATE` 行锁，锁内合并后写回。
- **③ 开考（扣次数 + 激活/新建答卷）无互斥**：连点、弱网重发、多标签并发开考 → **建出两张进行中试卷**（孤儿卷会被超时任务判成 TIMEOUT/0 分，污染成绩与统计）且**多扣考试次数**。修复：把"扣次数 + 激活/新建"串进同一把行锁（`student_attempts` 行 `FOR UPDATE`），锁内复查发现已被并发请求激活就复用，不重复扣次数、不新建。
- **④ 次数扣减"先自增再判断超限"**：超限抛错时自增已提交、不回滚 → 并发下多扣。修复：条件原子自增 `UPDATE … SET used_count=used_count+1 WHERE used_count < max_count`，影响 0 行才抛 1407。
- **⑤ `studentAttempt.upsert` 并发同键不原子**（本轮最值钱的一条）：Prisma 的 `upsert` 在并发同键时会退化成 SELECT+INSERT，**实测 8 并发开考有 7 个 500**，报 `Unique constraint failed on the constraint: student_attempts_student_id_exam_id_key`。修复：换成单条原子语句 `INSERT INTO student_attempts (…) VALUES (…) ON DUPLICATE KEY UPDATE updated_at = student_attempts.updated_at`。**并发热路径上"确保某行存在"不要用 upsert**，用 `INSERT … ON DUPLICATE KEY UPDATE`，或捕获 P2002 后当成功。
- **⑥ 顺带补的观测缺口**：全局异常过滤器 `AllExceptionsFilter` 对未预期异常只回「服务器内部错误」、**不写任何服务端日志**——上面第 ⑤ 条的根因就是靠补日志后一眼定位的。现已记录 方法+URL+message+stack。
- **实测证据（真实 MySQL，本机开发库）**：8 并发开考 → 全 201、**唯一 paperId**、`used_count=1`、试卷总数不变、服务端 0 异常；5 个题目并发存答案 → 5 个键全保留；8 并发交卷 → 全 201 同分、`SUBMIT` 事件**仅 1 条**；强制交卷（第 3 次 LEAVE）与手动交卷并发 ×3 轮 → 每轮只剩 1 条终态事件。
- **实测证据（2026-09-17 测试环境真库，构建 `index--ZBR24HL.js`）**：4 轮实测共 23 项断言全过——① 8 并发开考 201×8 / 0 个 5xx / 同一 paperId / 库内 1 张卷 / `used_count=1`；② 5 并发存答案 5 键全保留；③ 8 并发交卷全 100 分 / 1 条 SUBMIT / 1 张证书；④ 次数打满 10 → **400/1407** 且不多建卷；⑤ 强制交卷撞手动交卷 3 轮 → 每轮 `PAGE_HIDE×3 + SUBMIT×1`；⑥ **跨分钟 tick 抢跑**（tick 前 299ms / 后 15ms / 后 308ms）3/3 交卷赢、无 TIMEOUT 覆写、无悬空 SUBMIT；⑦ 已交卷卷在**两个超时条件同时成立**下被扫描器连扫 2 个周期仍 `SUBMITTED/100`；⑧ 真超时卷正常判 `TIMEOUT/0`（扫描器没被 CAS 改坏）；⑨ "每轮 8 并发开考"连做 3 轮 → 每轮唯一新卷、`used_count` 递增 1/2/3、进行中恒为 1（重考分支同样只建 1 张）。自测考试/试卷/次数行**全部清理为零残留**，清理后明细基线仍 73/23/50。
- **超时扫描不写 TIMEOUT 事件**（全库 TIMEOUT 事件数 = 0、TIMEOUT 卷 6 张）：验证"超时是否生效"要看**试卷状态 + 分数**，别去查事件表，否则会把正常行为当成 bug。
- **未修的建议**（按优先级）：组卷任务复用是"查了再建"无锁无唯一键（P2）；考试发布/关闭/删除仍是"先读后写"（P2）；统计接口在数据量放大后是重查询，建议加索引/预聚合（P2）；`DATABASE_URL` 未显式配 `connection_limit`/`pool_timeout`（P3）；组卷在事务内全量拉题库再内存洗牌（P3）；建考 60s 幂等键是进程内 `Map`，多实例失效（P3）。
- **避坑提醒**：
  - **状态机终结操作一律用"带状态的原子更新"（CAS）**，不要"先读状态再写"——读到的状态在写之前随时过期。凡是 `UPDATE … SET 终态` 的地方都要问一句"两个请求同时到会怎样"。
  - **整列 JSON / 计数类字段的读-改-写必须有互斥**（行锁，或 CAS 的 `SET x = x + 1` 形式）；前端 `Promise.all` 批量提交是最常见的触发场景。
  - 定时任务（每分钟扫描）是**额外的并发写入方**：改业务终态逻辑时要把定时任务一起算进去，它最容易"回头把已完成的事再改一遍"。
  - **500 必须能查**：异常过滤器不打日志时线上只有"服务器内部错误"，排查全靠猜；先补日志再排查，比读代码快得多。
  - 并发验证要用**真库 + 真并发**（`Promise.all` 打同一接口），单测 mock 不出锁行为；本次 8 并发开考一把就把 ⑤ 打出来了。

## 28. 并发容量：能扛多少人、数字怎么量、怎么别量歪（2026-09-17 容量评估，非缺陷）

> 触发：业务方追问「现在这个项目的并发可以同时多少学生在线考」。#27 修的是**正确性**（同时考会不会丢数据），这一条回答**容量**（同时考能站多少人），全部数字来自测试环境实测：真实账号走完整考试流程（开考→取卷→存答案→心跳→交卷）+ 并发压测，测完精确回滚。完整记录 [[lab-exam-2026-09-17-capacity-concurrency-assessment]]。

- **结论**：测试环境现状（单实例 + 应用与 DB 跨网）**安全 200~300 人同时在线**；500 人开始出现秒级延迟；生产把库放同机房后可期 **1000~3000 人**。
- **换算口径**：每学生稳态 **0.06~0.08 req/s**（30s 心跳 + 300ms 防抖存答案），答题活跃期 **0.10~0.12 req/s**——注意**每次改答案前端发 2 个请求**（存答案 + ANSWER 事件）。
- **实测基线**：读 `GET /api/student-exams?status=PENDING` 并发 1/5/20/50/100/200 → 11/23/60/121/**152**/93 req/s、零 5xx；写：开考 858ms（重考含建卷）、取卷 47ms、存答案 p50 186ms、心跳 p50 208ms、交卷 576~2221ms；同一张卷 50 并发 → 10 req/s（行锁串行化）。
- **瓶颈排序**：① 应用↔DB 网络路径（跨网 3~7 次串行 round-trip，单请求 45~292ms 里绝大部分是等网络；**同机房是最大杠杆且不改代码**）② Prisma 连接池未显式配置（默认 CPU×2+1，是当前事实并发上限；建议 `connection_limit=20~50` + `pool_timeout`）③ 单 Node 进程（无 cluster：单实例天花板 + 可用性单点）④ 每分钟定时任务（现 8~20ms，数据量放大后复查）。**已排除**：MySQL（`max_connections=1500`/用 10）、判分 CPU、组卷（后台任务 236ms/人、`BATCH_SIZE=5`，发布前跑完即可）。
- **避坑提醒**：
  - **压测先打一发探测请求确认 `code=0` 再上量**：本次第一版脚本把参数写成 `tab=pending`（真实是 `status`），而全局 ValidationPipe 对未知参数**直接 400** → 几百个请求"全部失败"，p50 38ms 的"好看数字"其实是拒答路径。**看到"吞吐高、延迟低、失败率 100%"这种组合，先怀疑测的东西不对。**
  - **别拿"同一张卷并发"的数字当真实容量**：同一张卷的所有请求会在 `papers` 行上串行化（实测 10 req/s）。真实考试每人一张自己的卷、跨学生不冲突，单卷数字只是"同一学生连点/多标签"的最坏情形，用它当容量会严重低估。
  - **容量必须用本系统 + 真实考试流程实测**：本次最大的瓶颈（跨网 DB 的 round-trip 等待）在读代码阶段完全看不出来。
  - **测完必须能精确回滚**：删新建的那张卷（`paper_questions`/`exam_events` 随卷级联）+ 恢复 `student_attempts.used_count`，再核验「卷集合 / `used_count` / 事件数 / 证书数」四项与压测前一致（本次实测 卷 7→6、`used_count` 2→1、事件 367→67、证书 0）。
  - **开考瞬间是唯一的重服务尖峰**（重考建卷 858ms/人）：千人同一秒点开考需要按班错峰或提前预热；组卷不在考试热路径上。
  - **单实例是可用性单点**：并发数字只说"站得住多少"，千级正式考试前要额外考虑多实例（应用无状态，唯建考 60s 幂等 `Map` 是进程内的 P3）。

## 32. Cookie+CSRF 双凭证对随登录/refresh 轮换，多标签页或顶号后旧页操作 403——页面笼统报错掩盖真实原因（自愈 `df072d5`）

> 触发：老师报「传感器题（数据完全合法）禁用成功、启用失败」，同账号 curl 直测 API 却 200。根因=CSRF token 是 `HMAC(密钥, JWT.jti)` 的**派生值**，每次登录/refresh 都轮换；cookie 浏览器级共享而 CSRF 在标签页自己的 sessionStorage——A 页 refresh 或 B 账号登录后，旧页旧 CSRF 配新 JWT → 403(1004) → 页面 catch 弹笼统「启用失败」盖住真实 toast「CSRF Token 缺失或错误」。

- **坑**：双凭证对（共享 cookie + 私有 CSRF）的存储形态天然会错位；**任何依赖"请求时两个都对上"的设计都要假设它们会脱同步**，并给前端一条"收到脱同步信号后如何恢复"的路径，否则用户看到的就是「系统随机翻脸」。
- **修复（`df072d5`）**：前端收到 1004 → 静默 refresh 换新 CSRF → `/auth/me` 核对账号与本标签页登录快照（`user_account`）一致 → 原请求重发一次（`_csrfRetried` 防循环、/auth/me 自身豁免防递归）。
- **红线：重试前必须核身份**——cookie 是共享的，若已被别的账号顶掉，盲目重试=冒名执行操作；身份不一致应清登录态引导重登，而不是重试。
- **排查套路**：操作随机失败/换浏览器就好 ⇒ 先怀疑本会话层坑；让报障人提供**完整报错截图**（区分 1004 vs 业务 400）；同账号 curl 直测三板斧。概念卡 [[concept-csrf-token-pair-rotation]]。
- **状态**：`df072d5` 已推 main，随下次发版上正式。

## 通用避坑清单（持续累积）

- 禁用/停用类功能：token 仍有效期内必须在鉴权层按用户状态拦截，不能只挡下次登录。
- 「提示 + 立即跳转」必丢提示：先模态确认、后跳转。
- 唯一性校验按业务语义跨字段，不按数据库字段名。
- 分页排序必须有稳定 tiebreaker。
- 提醒/通知类功能：先想清楚接收端在哪里，标记字段 ≠ 提醒送达。
- 统计/列表/导出的「状态」口径与及格线：必须由一个函数派生（单一事实源），及格线只允许来自 `paperConfig.passScore` 一处，禁止硬编码数值。
- 导出类功能必须绑定「上一次成功查询的参数快照」，导出时不要实时读表单当前值。
- 接口级权限校验的「范围」要与业务名单是同一实体（如 Paper 记录），用班级/学院等外围属性当边界必漏人。
- `el-upload`：`on-exceed` 与 `on-change` 互斥分支，limit 已满后新选择全走前者；业务请求与组件展示状态（handleStart）两条线都要覆盖。
- 唯一业务标识（工号/学号）字符集规则：「前端过滤 + 后端 DTO 校验」双保险；改规则先把自己的测试数据改合规。
- 给导出加新列：检查每一条行组装路径（不同维度导出常走不同循环），表头与行 key 漏配 = 「有表头无数据」静默缺陷。
- 聚合联表分组：先按过滤条件求匹配主键集合再收敛维度表，避免「外层全量 + 内层过滤」产出全 0 空组行；若业务要求默认展示全部分组（含 0），则维度枚举（全量）与计数过滤（匹配）分离，并区分「默认视图」与「筛选后视图」两种意图。
- Excel 中文列名与代码 row key 逐列对照，警惕「状态」与「学籍状态」等语义相近列混取。
- 本会话测试环境注意事项：测试数据测后需恢复；不要碰他人未提交改动 `web/e2e/statistics-scope.spec.ts`。
- **分子/分母同源**：任何「率」类指标（参与率、通过率、及格率）的分子与分母必须由同一组过滤条件派生；新增用户维度（如教师考生）时，改分母不改分子 = 指标静默失真，只有 >100% 这种反常识值才会暴露。
- 引入新考生类型/新角色维度时，按「统计分子→分母→分组表→筛选下拉→导出列→导出参数→排序→详情回落→搜索字段」九处清单过一遍，不要只改一个页面。
- 导出条数上限是业务决策：写死 `take: N` 前先问业务是否要全量；数据上限（应取消）与渲染上限（浏览器逐张渲染图片）是两回事，后者要保留并在界面给出替代路径。
- 「先暂存、后提交」的两阶段流程（草稿→发布、暂存单→提交单）：所有「人/名单」相关校验必须在提交那一刻复核，暂存期校验会过期；拦截后要给用户一条确认后可继续的出路。
- **「能导出」≠「用户知道导了什么、能只要哪一种」**：导出按钮旁要写清数据范围（含不含教师/某类考生），范围可切换时就给一个只作用于导出的选择器（别去动页面 KPI 口径）；切换选择器不应触发重新查询。用户问"是不是某人不能导"时，先用接口实测两个角色的返回行数和构成，再回答——本次实测证明"只有学院管理员能导教师"是错的前提，真实缺的是界面入口。
- **「贴边」类排版问题先量 x 坐标，不要凭感觉调 padding**：同一页面上不同块若有的包了带内边距的容器卡片（`art-card`，20px）、有的没包（裸 grid），对齐基准就有两套，肉眼看是"卡片和标题全都顶到边框"。判定基准 = 带边框卡片的 **border-box** 是否与内容块的**内容区**起算点一致；改法是让所有块同基准（要么都包卡片、要么都给补偿内边距），而不是给某一块单独加 margin 凑数。
- **「用户说没有某个功能」先确认功能是否只是不可发现**：本次「导出内容」下拉确实存在且生效，但无文字标签 + 默认值文案像 placeholder，用户直接没认出来。排查顺序：接口/产物里搜字符串证明功能在 → 再看它有没有可见标签、尺寸、位置是否像可交互控件 → 最后才考虑"真的没做"。
- 下拉/选择器类的**新控件必须带文字标签**，不能只靠默认值文案表达用途；带标签后要回归窄屏（390px）标题是否被挤换行。
- **「状态」这类派生字段有两种口径，别用一个函数套两处**：人数口径（按人最新一卷判定，服务 KPI/人数）与行口径（按每行实体自身判定，服务明细/导出）在"一人多卷"时结果不同；用人数口径去筛明细行 = 命中者的无关行全被带出且不报错。派生函数要按口径分开命名，并在调用处注释说明。
- **明细导出的筛选条件要落在"行自身"上**：行上带的外键（studentId/examId）只能用于限定范围，不能拿它做命中扩散（`IN (命中实体)` 会把该实体名下所有行都放出来）。
- **新维度接进统计后要检查"页面有没有行级视图"**：只有 KPI + 导出 = 用户必须导 Excel 才能回答"谁考了"（本次教师考生就是这样被业务方发现"不直观"）。
- **页面明细与导出必须共用一套筛选与行转换代码**（同 DTO / 同 where / 同行转换），并用单测比对"页面行 vs 文件单元格"+ 断言两者 where 全等——靠人工对照迟早漂移。
- **状态机终结操作（交卷/关闭/发布/删除）一律用带状态的原子更新（CAS）**，禁止"先读状态再写"；写之前先问"两个请求同时到会怎样"。
- **整列 JSON 与计数类字段禁止裸的读-改-写**：要么行锁（`SELECT … FOR UPDATE`），要么 `SET x = x + 1` 形式；前端 `Promise.all` 批量提交是最常见的触发器。
- **定时任务是额外的并发写入方**：它会把"已完成"的实体再写一遍，改终态逻辑时不能漏掉它（本次超时扫描会覆写刚交卷的卷子）。
- **Prisma `upsert` 并发同键不原子**（会退化成 SELECT+INSERT → 唯一键冲突 500）；并发热路径上"确保某行存在"用 `INSERT … ON DUPLICATE KEY UPDATE` 或捕获 P2002。
- **并发问题只能靠真库真并发复现**（`Promise.all` 打同一接口），单测 mock 不出锁行为；同时**500 必须在服务端留日志**，否则只有"服务器内部错误"四个字可查。
- **直连测试库改时间列必须用 `UTC_TIMESTAMP(3)`**（本次踩坑）：测试库会话时区是 `+08:00`，而应用按 UTC 读 DATETIME 列；用 `NOW(3)` 写会变成"8 小时后的未来"，超时任务判定 `shouldTimeout=false` **静默不触发**。验证定时任务时先确认时区，再下"任务没跑"的结论——本次差点误判成 cron 失效，实际是探针把时间写歪了。
- **定时任务类断言要按实现口径写，别凭想象写**：本次超时扫描**不写 TIMEOUT 事件**（只改状态+分数），断言写成"应有 1 条 TIMEOUT 事件"就会假失败；先读一眼实现或先查全库该事件类型的存量（总数=0 就是根本不产出）。
- **压测/联调先打一发探测请求确认 `code=0` 再上量**：未知 query 参数会被全局 ValidationPipe **直接 400**（本次 `tab` vs `status`），否则整轮数字全是"拒答路径"却看不出问题（失败率 100% + 延迟极低是关键信号）。
- **容量数字要连测量条件一起写**：同卷还是异卷、客户端并发数、客户端与库的网络位置。同一实体的行锁会把并发**退化成串行**（本次单卷 10 req/s），异实体并发才是真实形态；容量结论不给条件就是耍流氓。
- **应用与数据库的网络位置是隐藏的最大容量杠杆**：跨网时每个请求的 3~7 次串行 round-trip 会吃满延迟（45~292ms），同机房后同样的代码容量提升约一个数量级——部署选型阶段先定这一条，别等压测才发现。
- **高频"双请求"要合并**：本次前端每改一题发两个请求（存答案 + ANSWER 事件），而服务端存答案已刷新 `lastSyncTime`，合并可让答题期写请求量减半——但会动到监考事件流口径，属于要产品确认的优化。
- **界面文案用方位词（上方/下方/左侧）指代另一块 UI 时，改完版式要回头复核这些文案**：这类错误不报错、无测试覆盖、`grep` 也分不出对错，只能对着**最终版式**读一遍（本次三处全写反，#29）；核对时以 DOM 实际位置为准，别把"对的"也一起改掉。
- **多会话共用同一工作区：提交前先 `git diff` 分清哪些 hunk 是自己的**，「只 add 自己的文件」不够——同一个文件里可能混着另一个会话未完成的改动，必要时按文件级/行级剥离后再提交。
