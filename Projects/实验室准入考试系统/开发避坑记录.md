## 2026-08-14：删除/解除关联前未检查活跃考试导致越权

**现象**

管理端移除教师班级关联或删除班级时，没有检查是否存在进行中的考试。操作成功后，教师端再访问该考试直接报「越权」。

**根因**

`users.service.ts` 的 `removeTeacherClass` 和 `org.service.ts` 的 `removeClass` 只做了基础存在性/关联性校验，没有检查目标教师-班级或班级下是否存在 `status=PUBLISHED` 且当前时间落在 `[startTime, endTime]` 区间内的考试。删除或解除关联后，破坏了已发布考试的数据权限链路。

**正确做法**

任何会删除或解除教师-班级关联、删除班级的操作，都必须先检查关联考试中是否存在进行中的记录。`removeTeacherClass` 应只按班级检查，不应限制发布者：

```ts
const now = new Date();
const activeExam = await this.prisma.exam.findFirst({
  where: {
    classId: record.classId, // 移除 publisherId 限制
    status: ExamStatus.PUBLISHED,
    startTime: { lte: now },
    endTime: { gte: now },
  },
});

if (activeExam) {
  throw new BadRequestException({
    code: 1303, // 或 1204
    message: `该教师当前有进行中的考试「${activeExam.title}」，无法移除班级关联`,
  });
}
```

**避坑规则**

1. 删除或解除关联类操作，必须先识别其关联的「活跃业务资源」（这里是进行中考试），再决定是否允许删除。
2. 考试系统的核心资源（考试/试卷）必须先于组织架构变更完成或明确处理，不能先删组织再让业务链路断裂。
3. 涉及权限链路的破坏性操作，自测时除了正向通过，必须覆盖「有活跃资源时阻止」+「无活跃资源时允许」两类场景。
4. 错误码要和业务语义对应：`1303` 用于教师-班级关联相关，`1204` 用于班级相关，避免混用。
5. **同一后端接口可能被多个前端页面调用，修拦截逻辑时不要只盯一个页面入口；要确认所有 consumer 都走同一校验。**

## 2026-08-20 ~ 2026-08-21：批量修复记录（统计口径 / 数据导入 / 文件上传 / 年级兜底）

### Bug 1：班级管理列表「年级」列为空（管理 PC 端）

**现象**：班级管理列表部分班级年级列为空白，第一行（空年级排最前）必现，其余行正常。

**根因**：基础数据导入时源 Excel 年级列留空 → 数据库 `classes.grade=''`。修复时只改了 `src`，**没有重新 build，测试环境跑的是旧 `dist`**；且只给管理端班级列表一处做了兜底，`users.service.ts`（教师端班级名单/列表/班级管理员列表）和 `statistics.service.ts`（统计页班级维度）还有 5 处同一字段原样返回，同样为空。

**正确做法**：展示层统一走 `deriveGradeFromClassName(className)` 兜底推导（班名以「23」「2025」开头 → 4 位年份），5+1 处接口一处不落；同时提供 `backfill_class_grade.sql` 回填存量脏数据。

**避坑规则**

1. **改代码 ≠ 修复生效：改完必须重新 `npm run build`，`dist` 是部署产物**。怀疑"修了没生效"先查 dist 是否含新逻辑（`grep deriveGradeFromClassName dist/...`）。
2. 同一业务字段被多处接口消费（列表/统计/导出/教师端），修复时用 `grep -rn` 全局搜索该字段的所有返回点，一处不落，口径统一。
3. 导入数据允许缺列时，展示层要做兜底（推导/默认值），不能把空值直接摊到页面上。
4. 部署到测试环境后验证方式：页面 DOM 提取 + 直接调 API 检查字段值，两个独立数据源互相印证。

### Bug 2：学生数统计混入教职工（班级/学院/教师端）

**现象**：班级列表学生数、学院学生数、教师端班级名单人数把教职工（userType=1）也算进去，与"真实学生数"不符。

**根因**：`_count` 或名单查询只用 `{ classId }` / `{ collegeId }` 过滤，没加 `userType: 2`。同一个"学生数"统计在管理端、统计页、教师端各实现了一次，口径不一致。

**避坑规则**

1. "学生/教职工/管理员"是三类人，**任何人数统计都必须显式按 `userType` 过滤**，不能默认"该组织下所有人都是学生"。
2. 同义词口径（学生数/人数/名单）多端实现时，先建一个统计口径约定，改一端必须全局对齐所有端（本次就是先修统计、后补教师端、再补管理端的三连坑）。
3. 修复时检查所有 `count({ where })` 和名单查询的 where，防止漏网。

### Bug 3：题库重复导入同一文件生成重复数据

**现象**：同一题库 Excel 文件重复导入，每次生成一份重复题目，题库越导越臃肿。

**根因**：导入逻辑没有按业务唯一键（题型 + 分类 + 学院 + 题干）查重，直接 insert。

**正确做法**：导入前按业务键查重，提供"跳过/覆盖更新"两个模式；验证脚本改为纯 API 统计/清理，可直接面向测试环境跑。

**避坑规则**

1. **任何数据导入功能必须幂等**：按业务唯一键（不是数据库主键）判断重复，支持跳过或覆盖。
2. 导入类功能的验收必须包含"同一文件导两次"场景。
3. 测试/验证脚本不要依赖本地环境，用环境变量（如 `E2E_BASE_URL`）指向目标环境。

### Bug 4：全校统计按学院筛选/分组输出异常

**现象**：按学院筛选时其他学院数据被清零；不筛选时部分学院分组缺失（无学生学院不展示 0 行）。

**根因**：分组查询的 where 与分组集合不一致——筛选条件下只输出匹配学院，未筛选时又没把无数据学院补 0 行。

**避坑规则**

1. 分组统计要明确语义：**筛选时只输出匹配组；全景时输出全部组（缺数据补 0 行）**，两种模式都要测。
2. 筛选参数必须同时作用于「数据查询」和「分组集合」两层，只作用一层就会出现"数据清零"或"分组缺失"。

### Bug 5：教师班级统计「状态」筛选与列表列口径不一致 / 导出 Excel 结果状态列缺失

**现象**：统计页状态筛选器下拉选项与列表列展示的状态取值不匹配；导出 Excel 少结果状态列。

**根因**：筛选器、列表列、导出列三处对状态字段各自硬编码了一份取值集合/列定义，改一处漏其他处。

**避坑规则**

1. **筛选器、列表展示、导出列对同一字段（如状态）必须共用同一份取值映射**，不能各自硬编码。
2. 新增/修改枚举值时搜索全部 consumer（筛选选项、列渲染、导出列定义、后端 DTO）。

### Bug 6：工号/学号输入无字符集限制

**现象**：新增师生时工号/学号可输入任意字符，后端无校验。

**避坑规则**：**表单输入校验必须前后端双写**——前端限制输入（字符集/长度），后端 DTO 用 class-validator 同步约束，两处缺一不可。

### Bug 7：基础数据导入「再次上传新文件」页面文件名不更新 / 切换新 Excel 不生效

**现象**：第一次上传后，再选一个新 Excel 文件，页面文件名还是旧的，导入的还是旧文件。

**根因**：`el-upload` 的 `on-change` 在文件列表未变化时不触发；重复选择相同文件后 input 值未清空，change 不触发。

**正确做法**：监听原生的文件选择变化（强制清空 input value 或换用自定义 file input + change 监听；选定后清空 `:file-list`），确保同一文件可重选、新文件必刷新。

**避坑规则**

1. 上传组件（尤其 el-upload）的「重复选择文件」是经典坑：**换文件不生效、同文件不可重选**，实现时必须处理 input value 清空。
2. 凡依赖"文件变化事件"刷新的逻辑，都要考虑"连续选同一文件/第二次选不同文件"两个场景。

## 2026-08-13 ~ 2026-08-17 新增关键教训

### 1. 分页排序键必须唯一

- 事故：`orderBy: { createdAt: 'desc' }` 导致分页重复/漂移
- 做法：分页查询必须加唯一键 tie-breaker，如 `[{ createdAt: 'desc' }, { id: 'asc' }]`
- 关联：[[session-handoff-lab-exam-createdat-order-fix-2026-08-17]]

### 2. 统计口径分子分母必须统一

- 事故：全校统计参与率 120%（分子按试卷张数，分母按学生数）
- 做法：先定义统计单位（人/次/张），分子分母同口径
- 关联：[[2026-08-14 全校统计参与率超100%修复]]

### 3. 权限标志由后端统一计算

- 事故：考试过期后前端仍显示「重新考试」，点击报 400
- 做法：`canRetake` / `canDoX` 由后端返回，前端只读
- 关联：[[lab-exam-student-retake-400-fix-2026-08-13]]

### 4. 筛选条件必须追踪到最终查询

- 事故：`collegeId` 只做了越权校验，没写入 `where`，筛选被静默丢弃
- 做法：每个筛选参数都要追踪到最终 SQL/API 查询
- 关联：[[session-handoff-2026-08-14-证书ZIP导出与学院筛选修复]]

### 5. 数据格式约定四方一致

- 事故：判断题导入存 `TRUE`/`FALSE`，校验按 `A`/`B`，导致启用失败
- 做法：导入、存储、编辑、校验对同一字段的取值集合要对齐
- 关联：[[lab-exam-question-enable-judge-fix-2026-08-13]]

### 6. 表单输入必须前后端双限制

- 事故：前端无 `maxlength`，后端 DTO 也无校验，超长直击数据库 500
- 做法：前端加 `maxlength` + 提示；后端 DTO 按数据库容量设上限（不随前端收窄）
- 关联：[[session-handoff-2026-08-14-输入框字数限制与折行自适应]]

### 7. 列表刷新不清空跨页选中态

- 事故：搜索参考学生后清空全部已选，生成试卷遗漏学生
- 做法：用 `row-key` + `reserve-selection` + 全量集合自维护
- 关联：[[session-handoff-2026-08-14-输入框字数限制与折行自适应]]

### 8. 关键 bug 修复后必须落回测试断言

- 事故：判断题判分 bug 教训停留在文档，E2E 没覆盖判分断言
- 做法：事故复盘结论要转化为回归测试/CI 门禁
- 关联：[[2026-08-10 约束体系审核反馈]]

### 9. 改横切逻辑要全局搜索所有 consumer

- 事故：token 存储从 `localStorage` 切 `sessionStorage` 时漏改 axios 拦截器
- 做法：`grep`/`rg` 全局搜读写点；build 后检查产物残留旧关键字
- 关联：memory [[bug-lessons-and-self-check]] 6.2

## 通用规则速查

1. 开发/提交前读 `memory/bug-lessons-and-self-check.md`
2. 推送前跑：`vue-tsc --noEmit` + `npm run build` + `npm test` + `npx playwright test`
3. 修 bug 先写失败测试，再改代码
4. 任何删除/解除关联先检查活跃业务资源
5. 分页排序加唯一键 tie-breaker
6. 权限标志后端统一，前端只读
7. 筛选参数追踪到最终 SQL
8. 导入/存储/编辑/校验格式一致
9. 关键 bug 修复后加回归测试
10. 改全局状态/存储/过滤器时全局搜索 consumer
11. **改 src 必须重新 build 才能算修完，验证时先确认 dist 包含新逻辑**
12. **同一字段被多接口消费，用 grep 全量找返回点，一处不落**
13. **人数统计必须显式按 userType 过滤**
14. **数据导入必须幂等（业务唯一键查重，支持跳过/覆盖）**
15. 分组统计：筛选只出匹配组，全景补 0 行，两种模式都要测
16. 筛选器/列表列/导出列对同一字段共用一份取值映射
17. 上传组件重复选文件是经典坑：清空 input value，保证换文件/同文件重选都生效
