## 三、并发加固（v0.3.5 同批）

### 已修复 6 项

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | 交卷 / 切屏强制交卷 / 超时自动交卷三处终结都是无条件写库 | 连点交卷或切屏强制交卷与手动交卷撞车 → 重复写事件、重复发证；每分钟超时扫描会把**刚交卷的卷子覆写成 TIMEOUT** | 三处统一 CAS：`UPDATE papers SET 终态… WHERE id=? AND status='IN_PROGRESS'`；拿不到 CAS 不写事件/不发证；重复交卷回读已终结状态返回（不再 1404） |
| 2 | `papers.answers` 整列 JSON「读整列→改一题→写回整列」 | 交卷前前端并发刷写答案互相覆盖 → **丢答案丢分** | 事务内 `SELECT answers … FOR UPDATE` 行锁，锁内合并写回 |
| 3 | 开考（扣次数 + 激活/新建答卷）无互斥 | 连点/重发/多标签并发开考 → **建出两张进行中试卷**（孤儿卷被超时任务判 TIMEOUT/0 分污染统计）+ **多扣次数** | 扣次数与激活/新建答卷串进同一把 `student_attempts` 行锁，锁内复查复用已激活的卷 |
| 4 | 次数扣减"先自增再判断超限" | 超限抛错时自增已提交不回滚 → 并发多扣 | 条件原子自增 `… SET used_count=used_count+1 WHERE used_count < max_count`，影响 0 行才抛 1407 |
| 5 | 次数行用 Prisma `upsert` | 并发同键退化为 SELECT+INSERT → **实测 8 并发开考 7 个 500**（唯一键冲突） | 改 `INSERT … ON DUPLICATE KEY UPDATE` 单条原子语句 |
| 6 | 全局异常过滤器对未预期异常只回「服务器内部错误」，不写日志 | 500 无服务端痕迹（#5 就是靠补日志才定位到） | 未预期异常记录 方法+URL+message+stack |

### 实测证据（真实 MySQL）

- 8 并发开考 → 全 201、唯一 paperId、`used_count=1`、试卷总数不变、服务端 0 异常。
- 5 题目并发存答案 → 5 个键全保留。
- 8 并发交卷 → 全 201 同分、`SUBMIT` 事件仅 1 条、终态只写一次。
- 强制交卷（第 3 次 LEAVE）与手动交卷并发 ×3 轮 → 每轮仅 1 条终态事件。
- 门禁：`jest` 137 通过 / 11 文件，`nest build`、`vue-tsc -b` 全绿。

### 建议（未改）

- **P2** 组卷任务复用"查了再建"无锁无唯一键（学生级已有"已有试卷则跳过"兜底，重复建卷概率低）。
- **P2** 考试发布/关闭/删除仍是"先读后写"，两位管理员并发操作同一场考试可能互相覆盖。
- **P2** 统计接口在考生/试卷量放大后是重查询，建议加索引/预聚合。
- **P3** `DATABASE_URL` 未显式配 `connection_limit`/`pool_timeout`（默认 CPU*2+1）。
- **P3** 组卷在事务内全量拉题库再内存洗牌，题库大时锁持有时间长。
- **P3** 建考 60s 幂等键是进程内 `Map`，多实例部署失效。

## 四、踩坑记录（本轮新）

1. **Prisma `upsert` 并发同键不原子**：8 并发里 7 个 500（`Unique constraint failed on student_attempts_student_id_exam_id_key`）。要在并发热路径上"确保某行存在"，用 `INSERT … ON DUPLICATE KEY UPDATE` 或捕获 P2002，别用 upsert。
2. **500 必须留服务端日志**：`AllExceptionsFilter` 原先只回笼统文案，排查全靠猜；补日志后 30 秒定位根因。今后遇到"只有 code 1000"的 500，先确认过滤器是否打日志。
3. **本地验证环境要先确认"跑的是哪个构建"**：dev 期 `node dist/main` 不热更新，改完后端必须 `nest build` + 重启；本轮一度出现 `/statistics/candidates` 404（旧构建）与前端 `504 Outdated Optimize Dep`（两个 Vite 抢 5173 + 同一个 deps 缓存），都属环境问题而非代码问题。
4. **浏览器实操可委派**：右侧面板 Browser Use 对子代理不可用（`Browser is not available in subagent`），子代理改用本机 Chrome + Playwright（channel=chrome, headed）跑通同一套黑盒流程并产出真实截图。
5. **测试库直连改时间列必须用 `UTC_TIMESTAMP(3)`**（2026-09-17 测试环境复验时踩到）：测试库会话时区是 `+08:00`，而应用按 UTC 读 DATETIME 列；用 `NOW(3)` 写会变成"8 小时后的未来"，超时任务判定 `shouldTimeout=false` **静默不触发**，一度被误判成"每分钟的定时任务没跑"（同期库里有 07:09:00.018Z 等整分钟落的 TIMEOUT 卷，证明任务其实在跑）。改探针后超时项全过。
6. **定时任务类断言要按实现口径写**：超时扫描**不写 TIMEOUT 事件**（全库 TIMEOUT 事件总数 = 0、TIMEOUT 卷 6 张），断言写成"应有 1 条 TIMEOUT 事件"必然假失败。
