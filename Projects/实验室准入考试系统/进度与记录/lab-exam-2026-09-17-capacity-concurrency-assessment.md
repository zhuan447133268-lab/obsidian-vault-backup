# 2026-09-17 容量评估：同时多少学生可以在线考

> 触发：业务方追问「现在这个项目的并发可以同时多少学生在线考」。
> 方法：测试环境真实账号走真实考试流程（开考→取卷→存答案→心跳→交卷）+ 并发压测，测完精确回滚（零残留已核验）。

## 一、结论（先给数）

| 场景 | 同时在线考试人数 | 依据 |
|------|----------------|------|
| **测试环境现状**（单实例 + 应用与 DB 跨网络远程库） | **安全 200~300 人**；500 人开始出现秒级延迟；不建议 1000+ | 写路径实测有效并行度≈7、单请求服务耗时 186~292ms |
| **生产（DB 与应用同机房/同网）** | **1000~3000 人**可期（需显式配连接池） | 现有 186~292ms 里绝大部分是跨网 round-trip 等待，同机房后单请求可降到十毫秒级 |
| 单考试窗口的尖峰 | 开考瞬间是唯一重服务（重考建卷 858ms/人） | 300 人同一秒点开考需 ~40s 消化；按班错峰可消 |

一句话：**当前测试环境按 250 人规模做验收演练是安全的；要跑全院/全校千级并发，先做两件事——把库挪到同机房、显式设置 Prisma 连接池，然后按本文方法复测一次。**

### 顺带复验了 v0.3.5 并发加固（真库真并发）

- 60 并发写同一张卷：**23/23 答案键全部保留**（行锁合并没有丢答案）
- 交卷只产生 1 条终态、未重复发证
- 测试数据已精确回滚：卷 7→6、used_count 2→1、事件 367→67（300 条随机卷级联删除）、证书 0、考试仍 PUBLISHED

## 三、判定依据：每个学生需要多少请求

- 心跳：30s 一次 = **0.033 req/s**
- 每次改答案 → **2 个请求**（`POST /answers` + `POST /events`(ANSWER)），前端 300ms 防抖
- 答题活跃期 ≈ **0.10~0.12 req/s**；整场（30 分钟窗口）均值 ≈ **0.06~0.08 req/s**

承载力换算：写路径单请求服务耗时 186~292ms；读路径实测有效并行度 λ×ST = 152×0.045 ≈ **7**（与 Prisma 默认连接池同量级）→ 写路径吞吐 ≈ 7/0.25 ≈ **28 req/s** → 活跃期 ≈ 28/0.12 ≈ **230 人**，均值口径 ≈ 420 人。取保守区间 **200~300 人**。

## 四、瓶颈（按影响排序）

1. **应用↔DB 网络路径**（测试环境库在 192.168.0.165:13306，与应用跨网）：每个请求 3~7 次串行 round-trip，单请求 45~292ms 里绝大部分是等网络。**这是最大杠杆，且不需要改代码。**
2. **Prisma 连接池未显式配置**（`DATABASE_URL` 没有 `connection_limit`/`pool_timeout`，默认 CPU×2+1）——它就是当前的事实并发上限。建议显式设为 20~50 并设 `pool_timeout`。
3. **单 Node 进程**（docker-compose 只有一个 `server` 服务，`node dist/main`，无 cluster）→ 单实例天花板 + 可用性单点（挂了全挂）。
4. 每分钟定时任务（`autoTimeoutPapers`/`autoMarkAbsentPapers`）：现在扫描 8~20ms，数据量放大后要复查。
5. **单行锁**：同一张卷的所有并发请求串行化（实测 10 req/s）。真实场景每人一张卷、跨学生行不冲突，只有"同一学生连点/多标签"会撞——v0.3.5 已修。

### 已排除的瓶颈

- MySQL 侧完全不是问题：`max_connections=1500`、当前用 10、历史峰值 42；数据量很小（卷 206 / 事件 2310 / 题 5150 / 用户 8783），扫描 8~20ms
- 判分：交卷只有 2 次查询 + 内存里 25 题循环，CPU 可忽略
- 组卷：**后台任务**（建考时跑，`BATCH_SIZE=5` 串行），50 人 11.8s（≈236ms/人），发布前跑完即可，不在考试热路径

## 五、提高容量的可做项（按性价比）

1. **生产把 DB 与应用放同机房/同网**（不用改代码，收益最大）
2. **显式设置连接池**：`connection_limit=20~50`、`pool_timeout`（环境变量一行）
3. **合并"存答案 + ANSWER 事件"为一次请求**：前端每改一题发 2 个请求，而服务端 `saveAnswer` 已经更新了 `lastSyncTime`；合并可让答题期写请求量减半。属于 P2，代码改动小，但会影响监考事件流（`ANSWER_SYNC`），需要产品确认
4. **开考错峰**：按班分批开考 / 提前预热，避开同一秒的建卷尖峰
5. 真要跑到千级并发：**多实例横向扩展**（应用无状态：JWT/cookie + MySQL；唯一进程内状态是建考 60s 幂等 `Map`，属 P3，多实例会退化但不会写错）

## 六、复现方法（下次要在正式环境预演时照抄）

1. 用**自己的测试账号**登录（cookie + `X-CSRF-Token`），找一场自己名下 `PUBLISHED` 且未结束、`used_count < max_count` 的考试
2. `POST /api/student-exams/{examId}/start` 开考（会生成一张新卷）
3. `GET /{examId}/paper` 取题（答案格式 = `{questionId: ["A"]}`）
4. 压 `POST /{examId}/answers`（`{questionId, answer:[key]}`）与 `POST /{examId}/events`（`{eventType:'HEARTBEAT'}`）
5. `POST /{examId}/submit` 交卷后**回滚**：删证书 → 删新卷（`paper_questions`/`exam_events` 级联）→ `student_attempts.used_count` 恢复原值
6. 校验残留：卷集合、`used_count`、事件数、证书数四项与压测前一致
7. 坑：写时间列要用 `UTC_TIMESTAMP(3)`（测试库会话时区 +08:00）；`GET /api/student-exams` 的参数是 `status`（不是 `tab`，未知参数会被全局 ValidationPipe 直接 400）

## 七、本轮没做到的实测（如实记录）

- **没测"多账号、不同卷"的并发写**：测试环境只掌握一个学生账号。写路径数字取自"同一张卷"的最坏情形，跨卷（真实形态）只会更好，但没有实测数据支撑。
- 400 并发读失败发生在我本机（连接/端口上限），不代表服务端上限；服务端在 100 并发实测 152 req/s、200 并发劣化到 93 req/s，说明已在饱和区。
