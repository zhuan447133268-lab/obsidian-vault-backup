## 三、口径说明（既定行为，非缺陷）

- 乙「先考砸、重考进行中」在**成绩统计**显示「未通过」：`deriveOutcome` 优先级为 已通过 → 未通过（有已结束卷且未及格）→ 进行中（无任何结论卷时才显示）→ 缺考 → 未开始；逐次过程在「考试记录」表里可见。
- 状态筛选按**人**判定后带出该人的全部真实作答记录（`passed` 时丙那次未通过也会出现在「考试记录」，但不会带出未通过的人）。

## 四、本次新发现（工程侧）

1. **`GET /api/statistics/school` 的 `data` 是扁平的**（无 `summary` 包装）——验收脚本按旧记忆写 `data.summary` 直接崩。
2. **导出 xlsx 必须走 `arrayBuffer`**：`res.text()` + `Buffer.from(txt,'binary')` 会把 zip 写坏（`unzip` 报 missing bytes），但「文件大小 > 1000」的断言照样 PASS ⇒ 证据类断言必须落到「能被解析」。
3. **学院管理员的数据范围来自 `college_admins` 关联表**，不是 `users.college_id`（`DataScopeService` 明确注释「不自动包含自己人事归属的学院」）。只挂 `COLLEGE_ADMIN` 角色而不绑定学院 → `collegeIds=[]` → 明细/学院统计全 0 行。造测试账号时必须同时写 `college_admins`。

## 五、需要业务知情的一点

考生明细表 + 展开历次记录挂在**学院统计页**（`/college-admin/statistics`，角色 `COLLEGE_ADMIN`）；**全校统计页（`/school-admin/statistics`）没有明细表**（学校管理员直接访问学院统计页是 403）。后端 `GET /statistics/candidates` 对 SCHOOL_ADMIN 是放行的（本次 admin 调用正常返回 3 行），只是前端没在全校页渲染。该项在 [[待发版清单]] §五 已登记为「全校统计页也放一张考生明细表（P3 扩展，待业务确认）」。**2026-11-16 只读复核更正**：2026-09-20 记的「学院管理员 0 个」已过时——正式库现有 `COLLEGE_ADMIN` **23 个**，且 `GET /api/users/college-admins` 返回 23 条绑定、**未绑定学院范围的为 0**。所以这张明细表在正式是**有人会用的**，不构成发版阻碍；「全校统计页也放明细表」仍按 P3 待业务确认（纯前端，可随时加）。
