# 上线后问题复盘与质量改进（2026-11-17）

> 复盘范围：2026-09-18 正式 500 事故起，重点 2026-11-10 全校首次大规模使用 → 11-17 的 10 起真实反馈。
> **结论先行：不是"测试不认真"，是"测试的对象和生产不是同一个东西"。我们测了功能、测了部署，但没有测"生产数据 + 生产规模 + 生产拓扑"下的行为。**

## 一、事实清单：这 10 起到底是什么

> 这解释了为什么"单测全绿、功能验收全过"仍然会出问题：**我们擅长验证主流程，而生产暴露的几乎全是边界。**

## 二、为什么"测试环境测过、正式环境也测过"还是没抓到

### 缺口 1：测试环境是生产的"示意"，不是"副本"

四个不同构，每一个都足以让一类缺陷永久隐形：

| 维度 | 测试环境 | 生产环境 | 后果 |
|---|---|---|---|
| 数据分布 | 教育学院 0 题、缺 90 个班、无禁用生、无重复工号、无多次作答 | 250 题、296 班、有禁用生、有重复工号、有 3 次作答 | 数据类缺陷只在生产暴露 |
| 配置 | 部分限流/超时为测试放宽（登录 1000/5min） | 同一份放宽值被带上线 | 测试永远撞不到限流 |
| 规模 | 几个账号、串行操作 | 3000 人同一小时、并发改密/开考 | 并发/时序缺陷不可见 |
| Schema/迁移 | Jenkins 构建 + 迁移齐全 | 迁移靠人工执行，曾整库不在迁移管理内 | 缺列 500 |

**最关键的一句：当某个维度在测试环境是 0，该类缺陷的"测试通过"不是证据，是盲区。**

### 缺口 2：验收断言的是"过程成功"，不是"结果自洽"

我们习惯断言：HTTP 200/201、`code=0`、页面截图、条数对得上。这些只能证明"请求被处理了"，不能证明"数据是对的"。

- 导入回报"成功 250 条" → 150 条答案不在选项里，没人发现；
- 300 行/批返回 500 → 实际上已经落库，报错与状态不一致；
- 导出 xlsx 用 `res.text()` 落盘已损坏 → "size > 1000" 断言照样 PASS；
- 并发 append 写文件 → 退出码 0，但静默丢写。

**共同点：证据是"绿"的，系统是"错"的。** 这类假绿比没有测试更危险，因为它消耗了警惕。

### 缺口 3：只测"点"，不测"线"——状态机、时序、并发接缝

生产 bug 几乎都长在接缝上：

- 限流 × nginx × 前端重试 → 1009 → 无心跳 → 超时交卷；
- `close()` × 统计 × 学生列表 → 138 条假缺考 + 两张同名卡片；
- 发布 × 禁用学生 → 整批组卷失败；
- 通过 × 重考 × 证书 × 统计 → "一人多卷"口径争议。

我们测的是"每个接口单独调用对不对"，没有测"连续操作 5 步之后系统处于什么状态"，也没有测"两个请求同时到会怎样"。

### 缺口 4："正式环境测过" = 部署验证，不是行为验证

回看正式环境的验证动作，绝大多数是**只读**的：

- 抓入口 js、grep 分片标记串 → 证明"代码上线了"；
- `GET /api/exams`、`/api/statistics/school` 返回 200 → 证明"接口活着"；
- 假账号连续登录 12 次 → 证明"限流指纹在"；
- 页面截图 → 证明"能打开"。

这些都对，但它们证明的是**部署成功**。真正的写路径（改密、答卷、组卷、导入、关闭考试）我们**刻意没有在生产做**——这是对的，出于安全。但结果是：**写路径的缺陷只能等真实用户来触发。**

所以缺的不是"再测一遍正式环境"，而是中间那一层：**在生产同构的数据上做写入型预演**（测试环境 + 真实文件 + 真实数据形态 + 生产配置）。

### 缺口 5：存量数据没有主人，运行期没有监控

- 选项 D 从 09-02 潜伏到 11-10，两个月里没有任何一次全库体检；
- 138 条假缺考在库里躺了几天，是老师截图才被发现；
- 重复教师号从 08-28 躺到 11-17；
- 1009 事故是老师打电话，不是告警。

**代码测试只能保证"新写入正确"，保证不了"库里已有的对不对"。** 数据类问题必须靠独立的数据巡检，不能靠功能测试。

### 缺口 6：产品语义没有"签字"

三个最贵的坑都不是实现错误，是语义没对齐：

- "关闭考试"：用户以为"作废/取消"，代码做成"结束 + 给未开考的人盖缺考"；
- "重新考试"：用户以为"重考一次覆盖结果"，系统记成多条作答记录，统计口径随之分裂；
- "删除账号"：用户以为"删掉这个人"，schema 里 `Paper/Exam/Certificate` 全是 Cascade，裸删会连带删成绩。

**功能测试测的是"代码按我写的逻辑运行"，测不出"我写的逻辑不是用户要的"。**

### 缺口 7：验证者 = 实现者，盲区完全重合

我设计修复，再用同一套心智模型设计验证——如果我对"关闭"的理解错了，我的测试也会跟着错。所有这些问题都"通过"了我的验收，不是偶然，是**系统性相关**。

再加上证据标准偏"绿"（状态码、条数、截图），就形成了稳定的假阳性流水线。

## 三、我自己的三处失误（不推给流程）

1. **把"测试环境通过"当成了"生产可用"的证据**，没有先问一句："这个结论依赖哪些测试环境特有的条件？换个数据/配置/规模还成立吗？"
2. **验收设计沿用了实现的心智模型**：我测的是"我写的逻辑对不对"，不是"用户会怎么把它用坏"。
3. **证据标准不够硬**：三次假绿（并发 append、xlsx 损坏、300 行批次）都是同一个毛病——**断言了"动作发生了"，没断言"结果是对的"**。

## 四、改进方案：三道闸门 + 两条兜底 + 一条制度

### 闸门 1：发版前（Release Gate）

**1.1 变更影响面清单（每批必填）**

每个 commit 回答四件事：

- 改了哪些路由 / 表 / 状态机 / 定时任务 / 前端页面 / 配置项？
- 每一项对应哪条用例、什么数据前置、期望什么不变量？
- 这次改动在什么数据下会出错？生产有没有这种数据？
- 如果出错，用户会怎么发现？我们能不能提前模拟？

没有影响面清单的批次不发。

**1.2 环境同构核对（只读，5 分钟）**

- 迁移：测试/正式 `_prisma_migrations` 计数、本次涉及表的 `SHOW COLUMNS`；
- 配置：限流阈值、超时、连接池、`AUTH_MODE` 逐项 diff，**测试放宽值必须显式标记并收回**；
- 数据分布：本次涉及的实体（学院/题库/班级/学生/考试）两边计数与关键维度对比；某维度为 0 ⇒ 标为盲区，必须造 fixture。

**1.3 边界数据集回归（永久保留在测试库）**

这是**投入产出比最高的一项**。把生产真实出现过的"脏状态"固化成常驻数据：

| 编号 | 夹具 | 覆盖的坑 |
|---|---|---|
| F1 | 一个班含 1 名禁用学生 | 组卷整批 1200 |
| F2 | 同学院同名、工号不同的两条教师 | 重复工号 |
| F3 | 同一学生同场 3 份卷（通过/超时/进行中） | 一人多卷、统计口径 |
| F4 | 一场"建了就关"的考试 | 138 假缺考 |
| F5 | 同名两场考试（一场作废、一场真实） | 学生端两张卡片 |
| F6 | 教育学院 250 题 + "表头整格清空"Excel | 选项 D 丢失 |
| F7 | 3457 行学生 Excel | 导入 500 |
| F8 | 一个 0 题学院 / 一个 0 学生班级 | 空数据分支 |
| F9 | 已通过学生再次开考 | 1409 / 重考 |
| F10 | 3000 人并发账号池 | 限流/连接池/超时 |

每个夹具配：建数据脚本、期望不变量、清理脚本。每次发版前跑一遍。

**1.4 破坏性操作清单**

`发布 / 关闭 / 删除 / 重置密码 / 导入 / 导出` 六类，每一类必须有一条"操作前状态 → 操作后状态"的断言，不能只验"接口 200"。

**1.5 迁移门禁**

- 首选：容器入口执行 `prisma migrate deploy`；
- 备选：发版前校验 `_prisma_migrations` 计数 + 本次新列的 `SHOW COLUMNS`，不符即拒绝发版。

### 闸门 2：验收标准（Definition of Done）

**2.1 每个 bug 必须有一条"会红的测试"**

先写能在旧代码上失败的用例，再修。数据类 bug 的"测试"就是一条不变量 SQL。

**2.2 不变量清单（本项目专用）**

| 域 | 不变量 |
|---|---|
| 题库 | `answer ⊆ options`；非判断题选项数 ≥ 2；题干非空；`JSON_LENGTH(options)` 与答案键匹配 |
| 导入 | `created + updated + failed = 文件行数`；逐行字段等同源；失败行必须有原因 |
| 组卷 | 每人一份卷；题量 = 配置；无重复题；无禁用/无效考生；失败点名到人 |
| 考试 | `sum(papers by status) = 应考人数`；`close` 不改卷；交卷分数 ∈ [0,100]；只有 1 条 SUBMIT 事件 |
| 统计 | KPI 人数口径 vs 明细行口径有明确定义；导出与明细同源；分子/分母同源 |
| 账号 | 学号/工号唯一；同学院同名同号告警 |

**2.3 证据质量四条规则**

1. 断言**值**，不只断言状态码；
2. 文件类必须**回读**（xlsx 用 openpyxl 读回，zip 用 `unzip -l`），不能用 size 判断；
3. 并发类必须**前后快照 + 逐行比对**；
4. 任何"0 结果"都要有**正向对照**（同一个查询加已知命中的过滤条件应能返回），防止查询本身写错；
5. 破坏性脚本必须有**反例夹具**：构造一批"不该被改"的行，断言它们零改动（`11_` 的 25 行对抗 fixture 就是范本）。

### 闸门 3：上线后 30 分钟（Production Probe）

**3.1 只读业务探针**（不是 bundle hash）

- 关键 API 200 + 关键字段存在；
- 统计自洽：人数/卷数/缺考数能对上；
- 题库不变量、重复身份、孤儿卷查询；
- 限流指纹（假账号 10 次）。

**3.2 写入型冒烟**（专用测试账号，测后清理）

开考→答题→交卷→证书；改密；组卷；导入 2 行小文件。

**3.3 监控告警**（当前最大的空白）

最小可用版：每 5 分钟跑一次，异常推钉钉：

- 5xx > 0 / 1009 > 20 / 429 突增；
- 登录失败率 > 30%；
- `TIMEOUT` 卷 > 5 张/10 分钟；
- 未到结束时间却出现 `DRAFT→ABSENT`；
- 导入失败 > 0；
- 题库/孤儿/重复身份不变量非 0。

### 兜底 1：数据体检（nightly audit）

把上面的不变量写成一套只读 SQL，每晚对正式库跑一次，非 0 即告警。**这是唯一能覆盖"存量脏数据"和"两版之间的静默损坏"的机制。**

### 兜底 2：可观测性与开关

- 结构化日志 + request id（已有部分）；
- 限流开关 `THROTTLE_ENABLED`（已有）、导入批大小、超时阈值、功能开关；
- 事故 runbook：1009 → 查分桶键；导入 500 → 查事务超时；缺考 → 查 close 语义；登不上 → 查强制改密。

### 制度：复盘三问 + 同类扫描

每起事故必须回答：

1. 为什么测试没抓到？缺的是哪个层级（数据/配置/规模/状态机/语义）？
2. 补了什么（测试/巡检/监控），它能在旧代码上变红吗？
3. 同类问题还有没有存量？给出全库扫描 SQL，结果为 0 才算闭环。

## 七、一句话总结

> **测试环境的职责不是"证明功能能用"，而是"证明它在生产的数据、配置、规模和拓扑下也能用"。**
> 前者我们已经做得不错；后者才是最近这批问题的真正来源。
> 补的不是更多测试用例，而是**生产同构的预演 + 结果不变量 + 运行期监控**。
