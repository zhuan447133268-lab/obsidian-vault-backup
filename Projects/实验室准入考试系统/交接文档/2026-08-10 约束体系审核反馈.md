# 2026-08-10 约束体系审核反馈

> 触发：对项目 `D:\2026准入题库` 做架构约束体检，结合《架构师的工作交付与 AI Coding 时代的约束设计》五层约束框架。
> 结论一句话：**规格与文档（给人看的交付）做得好；机器可执行的约束门禁（给机器读的规则 + CI + 测试）缺失。**

---

## 一、项目现状（客观盘点）

功能完整的实验室准入考试平台，非雏形：
- 后端 NestJS + Prisma + MySQL + Redis，前端 Vue3 + Element Plus
- 五大模块：组织权限（学校-学院-班级-教师分班）、题库、考试（组卷/发布/补考/防切屏/自动交卷）、证书、统计导出
- 数据范围隔离（SchoolAdmin/CollegeAdmin/Teacher/Student + `data-scope.service.ts`）
- 14 个 Playwright E2E（student-flow、makeup-flow、force-submit-flow、statistics-scope 等）
- 交付文档完整：接口契约、数据库设计、部署手册、验收清单、Session-Handoff
- git 提交规范 `type(scope): description`，`.env` 与备份 SQL 已正确忽略

---

## 二、对照五层约束体检

【第一层：规则文件（AGENTS.md/CLAUDE.md/.cursorrules）】❌ 完全缺失
项目根目录无任何给 AI 读的规则文件。AI 打开仓库只能靠猜：技术栈版本、目录职责、禁止事项、安全红线均未写死。最便宜、最该补的一层。

【第二层：规格前置】✅ 亮点（Obsidian 知识库支撑）
PRD（需求确认文档）、学生考试作答端 API 设计 v1.0、第六阶段统计导出、生产环境数据库导入清单、阶段性验收清单——契约先行做得相当好。Spec 层是架构师本职，已达标。

【第三层：架构边界的可执行测试】❌ 缺失
- 单元测试仅 1 个（app.controller.spec.ts，脚手架默认）
- 无 ArchUnitTS / dependency-cruiser 依赖规则测试
- 大量 `verify_*.js` 一次性脚本散落 server 根目录，非可回归自动化测试

【第四层：静态分析与门禁】❌ 缺失
- 无 ESLint 配置（server/web 均无）
- 无 CI pipeline（无 GitHub Actions / GitLab CI）
- 无覆盖率门槛、密钥扫描、依赖白名单
- 代码能否合全靠人工 review，无机器把关

【第五层：可观测性】⚠️ 部分
- 有全局异常过滤器、健康检查、请求限流——基础不错
- 无统一结构化日志、无指标暴露（RED）、无追踪埋点规范
- 防切屏事件审计（ExamEvent）已记录，值得肯定

## 三、修正：不是缺"脑子"，是缺"机器执行的门禁"

上一版判断"缺规格层"**收回一半**。Obsidian 显示规格层做得好。真实结论：

约束现在都「写给人看」（Obsidian 文档、需求确认、交接），没有「写给机器执行」（AGENTS.md、CI、ESLint、架构测试）。知识库是优秀的"给人看的交付"，缺的是"给机器读的规则 + 确定性门禁"这两类新交付。

## 四、能从现有记录直接改进的实事

1. **判断题判分 bug（07-21）——"教训停留在文档，没变成门禁"**
   交接自述："E2E 18/18 全绿也没抓到——断言没覆盖判断题得分。判分类核心断言是 E2E 必备项。"
   教训应为：事故复盘结论要落回测试断言，而不能只写交接文档。这正是"约束要可演进"。

2. **王卓尔越权（07-29）——数据范围无单测**
   根因是 `buildFilterWhere` 对 COLLEGE scope 的 classId 校验。跨角色数据隔离逻辑应补单测（data-scope.service.ts / users.service buildFilterWhere），现在靠实测+临时 Playwright，无回归保护。

3. **需求确认文档"待确认"项 vs 代码已实现默认值——缺 ADR**
   多选判分、及格线(≥80)、切屏强制交卷、考试次数默认10 等已实现但未确认。已实现未确认的规则是"默许的架构决策"，建议补成轻量 ADR 并标进需求确认文档确认区。

4. **教师分班是上线关键路径（已知数据缺口）**
   生产导入清单 FAQ 明说"实验教师名单 Excel 无班级信息"。非代码问题但阻塞上线，需单独列待办盯。
