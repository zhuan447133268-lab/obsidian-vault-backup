S13 缺陷② · 教师看板 60 万次页读 / 一次请求（与缺陷①同一类病：聚合查询不带覆盖索引）
==============================================================================
发现路径：缺陷①修完、class 档通过后，顺手量了一次「空闲态教师看板」，发现单发一次
          /api/admin/dashboard 要读 20.9 万行、60.3 万次逻辑页读、耗时 524~590ms。
          这是一次请求的开销，且落在老师每节课都会打开的那一页上 —— 于是按同一套方法查到根因。

量法（开工惯例，与缺陷①完全一致）：
  · Innodb_rows_read / Innodb_buffer_pool_read_requests 增量（逻辑页读不受并发噪声影响）
  · EXPLAIN 的访问方式（ALL / index / ref / Using index）
  · 有索引与否用同一秒内的 IGNORE INDEX 对照，避免跨时间采样
  · 每条 SQL 单独跑一遍，量出「哪一条背了这笔账」，不靠猜

二、两个根因

根因 1（纯代码，与索引无关）：同一个聚合在一次请求里算了两遍。
  teacher_service.go 里看板先算 xpSumsThisWeek(studentIDs, thisWeek)（数据卡要），
  随后 attendCount(...) 内部又调 xpSumsBetween(userIDs, thisWeek, now) ——
  同一张账本、同一个时间窗。④ 与 ⑥ 两次测量的数字一模一样（74,614 行 / 225,362 页）就是证据。
  校级汇总（/api/admin/school）的循环里同样是每班两份。按一半浪费算，这一项就占了全部页读的 37%。

根因 2（索引不带筛选列）：「本周 XP 求和」的条件是 user_id IN (...) AND created_at 区间，
  原有复合索引 (user_id, delta) 与 (user_id, created_at) 都不含全部三列，
  MySQL 只能选一种：拿 user_id 定位、再逐行回表补另一个条件。
  EXPLAIN: type=index key=idx_xp_ledger_user_id rows=74372 Extra=Using where → 回表 7.4 万次。

三、索引候选试装（先量后改，试装可逆）

候选 A：xp_ledger(user_id, created_at, delta) —— 让「按周求和」变成覆盖索引
候选 B：attempt_answers(attempt_id, created_at, question_id, is_correct) —— 让薄弱知识点 JOIN 走索引内取数

查询                    基线扫过行/页读/耗时        装 A+B 后                同秒 IGNORE INDEX 反证
本周 XP 求和            74614 / 225362 / 213.0ms    74614 / 1751 / 73.5ms    74614 / 225362 / 211.6ms
                        EXPLAIN: idx_xp_ledger_user_id / Using where
                        → idx_xp_ledger_user_created_delta / Using index（覆盖，不回表）
薄弱知识点 JOIN           56235 / 150414 / 195.8ms    56235 / 75440 / 144.6ms   56235 / 150414 / 184.9ms
                        → idx_attempt_answers_attempt_created / Using index

  A 的效果：页读 225,362 → 1,751（129 倍）。IGNORE INDEX 同秒跑回 225,362，排除时间因素。
  B 的效果：页读 150,414 → 75,440（2 倍）、耗时 -26%。剩下的页读是 questions 表按主键取标签
            （每条答案一次），而 knowledge_tag 在题库表上，不许加列（表结构冻结 17 表/128 列），
            索引层面到此为止 —— 这条查询的下降空间已经用完。
  两个索引都写进了模型（AutoMigrate 幂等建），并把被 A 完全覆盖的旧索引
  idx_xp_ledger_user_created 删掉（它是 A 的前缀，留着只是写放大）。

六、口径与复现

  口径：看板是教师端页面，前端只在打开/切班时拉一次（已 grep 确认无轮询定时器），
  所以真实场景是「每节课几次」，不是每秒一次。修复的意义不在 QPS，而在于：
  一节课里 40 个学生在答题的同时，老师点开看板不该等半秒、也不该让库去读 60 万个页。

  复现：

    python s13_dashboard_queries.py                                                        # 逐条 SQL 拆账
    python s13_dash_idx_ab.py                                                              # 索引 A/B 与同秒反证
