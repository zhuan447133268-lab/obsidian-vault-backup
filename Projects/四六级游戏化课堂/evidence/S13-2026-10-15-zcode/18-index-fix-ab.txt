S13 压测暴露的缺陷 · 修复前后对拍（试点库 cet46_pilot@3306，55,006 行 xp_ledger）
==============================================================================

量的是三条查询：
  ① 看板/名单·按用户求和 XP     SELECT user_id, SUM(delta) ... WHERE user_id IN (41 个 id) GROUP BY user_id
  ② 登录/地图·连续周派生       SELECT user_id, created_at ... WHERE user_id IN (...)  → 改按 DATE() 分组
  ③ 交卷·按单据查流水          SELECT reason, SUM(delta) ... WHERE ref_type=? AND ref_id=? GROUP BY reason

三项数据：EXPLAIN 的访问方式 / 服务端耗时 / Innodb_buffer_pool_read_requests 每次请求增量（逻辑页访问）。
逻辑页读不受并发噪声影响，是「回表 / 全表扫」最硬的证据。

阶段一（修复前，索引尚未建立）：已建索引 = 无
阶段二（修复后，新二进制启动时迁移出索引）：已建索引 = ['idx_xp_ledger_ref', 'idx_xp_ledger_user_created', 'idx_xp_ledger_user_delta']
阶段二还多跑了一组 IGNORE INDEX：同一份数据、同一秒内把「没有该索引的行为」再跑一遍，避免跨时间采样。

结论（按测量值，不按感觉）：
  ① 覆盖索引 (user_id, delta)：每次请求的逻辑页读从 165,666 降到 911（182 倍），
     耗时中位 114 ms → 19 ms。EXPLAIN 从 idx_xp_ledger_user_id 的回表变成 Using index。
  ② 连续周派生：SELECT 回给 Go 的行数从 55,006 行降到 40 行（今天全部流水只落 40 个「用户×日」组），
     EXPLAIN 从全表 ALL 变成覆盖索引 Using index；耗时中位 76.9 ms → 35.6 ms。
     换按天分组后 Go 侧不再接收/解析 5.5 万行切片——这才是登录链路上真正的省。
  ③ 交卷链路 (ref_type, ref_id)：EXPLAIN rows 从 53,105 降到 2，耗时中位 21.3 ms → 0.54 ms（40 倍），
     而且是每次交卷跑两遍的查询。

三条查询在压测里各自代表一条链路：看板/名单、登录/地图、交卷。
索引是 GORM AutoMigrate 在服务启动时建的（幂等、只加不删），启动日志里有 CREATE INDEX 行：
  logs\server.log  →  [245.960ms] CREATE INDEX `idx_xp_ledger_ref` ON `xp_ledger`(`ref_type`,`ref_id`)
